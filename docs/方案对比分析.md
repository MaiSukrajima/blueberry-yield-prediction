## 第一部分　方案对比分析

### 1. 两个方案的定义

| | 方案 A：沿用原数据源 | 方案 B：改用现数据源 |
| --- | --- | --- |
| 数据 | `DeepBlueberry Challenge 2025` 竞赛数据（15,000 行） | Kaggle Datasets 公开数据集（777 行） |
| 获取 | 需竞赛受邀身份 | 公开下载端点，无需认证 |
| 现状 | **无法获取**（接口 401） | 已落地并核验 |

需要先说明一个前提：方案 A 并非"我们主动不选"，而是**技术上走不通**。该竞赛为邀请制，
`api/v1/competitions/download-all/…` 在本机实测返回 401，即使拿到 API Token 也无权下载。
因此这份对比的实际意义是：**在被迫更换的前提下，换来的这份数据是好是坏、代价多大**。

### 2. 数据内容对比

#### 2.1 规格

| 项目 | 方案 A（竞赛版） | 方案 B（公开版） |
| --- | --- | --- |
| 形状 | 15,000 × 19 | **777 × 18** |
| 文件数 | 3（train / test / sample_submission） | **1** |
| 标识列 | `id` + `Row#` | 仅 `Row#` |
| 特征列 | 16 | 16（完全相同） |
| 目标列 | `yield` | `yield` |
| 缺失值 | 0 | 0 |
| 完全重复行 | 0 | 0 |
| 预置测试集 | 有，10,000 行无标签 | **无** |
| 许可证 | CC BY 4.0 | CC BY 4.0 |

**16 个特征列名与顺序完全一致**，目标变量同名。这意味着两人的代码不需要改列名映射，
迁移成本主要落在"行数"和"没有 test.csv"这两件事上。

#### 2.2 数据性质：这是最容易被忽略、也最要紧的差异

`yield` 的极值在两版中**完全相同**（min 1637.704022、max 8969.401842），说明二者同源。
但逐行比对后可以确定：**它们不是母本与副本的关系，而是同一仿真模型的两批独立运行结果。**

实测证据：

| 检查项 | 结果 | 说明 |
| --- | --- | --- |
| 16 特征组合 + yield 逐行精确匹配 | **1 / 15,000（0.01%）** | 几乎找不到完全相同的行 |
| 按 `Row#` 对齐后 `clonesize` 一致率 | 93.3% | 场景设定部分大多保留 |
| 按 `Row#` 对齐后温度六列一致率 | **36.4%** | 环境参数大多被重新抽样 |
| 按 `Row#` 对齐后 `fruitset` 一致率 | **0.4%** | 模拟输出几乎全部不同 |
| 方案 A 每个 `Row#` 的行数 | 平均 19.33，最多 72 | 同一场景约 19 次重复运行 |

也就是说，方案 A 的 15,000 行 = 约 777 个场景 × 每个场景约 19 次重复仿真，
**每次重复时温度、降雨等环境参数重新抽样**，`fruitset`/`yield` 随之重新计算。
方案 B 的 777 行 = 每个场景一条记录。

**这个差别直接改变了数据的信噪比**：

| 特征与 `yield` 的相关系数 | 方案 A | 方案 B | 差 |
| --- | --- | --- | --- |
| `fruitset` | +0.9504 | **+0.9841** | +0.034 |
| `seeds` | +0.9197 | **+0.9612** | +0.042 |
| `fruitmass` | +0.8867 | **+0.9304** | +0.044 |
| 温度六项（逐个） | **≈ −0.004** | **≈ −0.18** | −0.18 |

方案 A 里温度字段与产量的相关性**几乎归零**，方案 B 里稳定在 −0.18 左右。
原因不难理解：同一场景被重复约 19 次且环境参数重新抽样，温度对产量的作用被平均掉了。

#### 2.3 关于 `Row#`：一处需要更正的历史表述

v1.x 文档写过"`Row#` 携带组信息，会造成数据泄漏，必须用 GroupKFold"。本次做了检验：

| 切分方式（方案 A 数据，Ridge） | OOF MAE |
| --- | --- |
| 随机 5 折 KFold | 274.87 |
| 按 `Row#` 分组 5 折 GroupKFold | 274.79 |

**差 0.08，不到 0.03%。** 把 `Row#` 直接作为特征入模，MAE 也只从 274.87 变成 274.95。

结论：方案 A 的 `Row#` 虽然结构上有分组（776 个值重复 14,224 次），但由于组内特征被重新抽样，
**实测并未产生泄漏**。"必须用 GroupKFold"这一条属于理论推断，不成立。

在方案 B 中 `Row#` 是 0–776 的连续行号，唯一对应每行，`nunique = 777 = 行数`。
**它仍然不能入模**——理由不是泄漏，而是它只是样本序号，没有任何生物学含义，
入模会让模型记住"第几号样本"而非学习规律，且无法对样本外数据使用。

### 3. 指标结果对比（同口径实测）

两版数据各自跑同一组模型，切分口径统一为：5 折随机 KFold，`shuffle=True`，`seed=42`，
只用 16 个特征。

| 模型 | 方案 A MAE | 方案 B MAE | MAE 变化 | 方案 A R² | 方案 B R² |
| --- | --- | --- | --- | --- | --- |
| 常数基线（训练折均值） | 1110.83 | 1109.41 | −0.1% | −0.0000 | −0.0055 |
| **Ridge（标准化, alpha=1）** | **274.87** | **98.74** | **−64.1%** | 0.9100 | **0.9907** |
| RandomForest（100 棵） | 256.98 | 116.10 | −54.8% | 0.9212 | 0.9868 |
| HistGradientBoosting（默认） | 246.46 | 113.53 | −53.9% | 0.9267 | 0.9859 |

三件事值得单独说明：

**① 误差下降不是模型变强，是数据变干净。** 常数基线两版几乎一样（1110.83 / 1109.41），
说明 `yield` 本身的离散程度没变；变的是模型能利用的信号强度。R² 从 0.91 升到 0.99 也是同一件事。

**② 模型排序反转了。** 方案 A 上树模型更好（HGB 246.46 < Ridge 274.87）；
方案 B 上线性模型反超（Ridge 98.74 < HGB 113.53 < RF 116.10）。
原因是 `fruitset` 与 `yield` 的相关系数达 0.984，关系接近线性，而 621 行的训练集
对树模型来说容量过剩、容易过拟合。

**③ 与 v2.0 交付的 98.79 有 0.05 的差异**，这属于折划分方式不同导致的正常波动
（v2.0 用按 `yield` 十分位分层的 KFold，本节用普通随机 KFold）。以项目内 `baselines.py`
的分层口径 **98.79** 为准，本节数字仅用于跨方案横向比较。

### 5. 优劣分析

**方案 A（沿用竞赛版）**

- 优势：样本量大 19 倍，可训练高容量模型；有官方测试集，可模拟完整提交流程；与分工文档原文完全一致，无需向老师解释变更。
- 劣势：**无法获取，这是决定性的**；温度特征与产量相关性接近 0，环境类特征基本失效，特征工程的发挥空间被压缩；`Row#` 存在组结构（虽实测无泄漏，但需额外论证）。

**方案 B（改用公开版）**

- 优势：**可公开获取、可脚本复现**，任何人 clone 后一条命令拿到同一份数据；数据是原始记录，条件—产量关系完整，温度特征恢复有效；`Row#` 退化为纯行号，无需再讨论分组切分；学术源头明确（Obsie et al. 2020，Mendeley DOI），两个独立上传者的文件逐字节相同，真实性可自证。
- 劣势：样本仅 777 行，5 折后每折验证集 124 行，**分数波动明显变大**（Ridge 各折 89.6–106.2，标准差约 6.6）；无官方测试集；与分工文档"下载 train/test"的表述不符，需要在报告中说明。

**综合判断**：方案 B 是唯一可行的选择，且质量上更好。代价是样本量，但换来的是干净、可复现、可溯源的数据。
真正的风险不在数据本身，而在**团队里其他人不知道这些变化**——这靠交接文档解决，也是本轮修订的目的。
